# План реализации HabitTrack

## Статус

Документ фиксирует организационно-инженерный план перехода от анализа и
проектирования к реализации рабочего клиент-серверного приложения HabitTrack.
Код приложения на этом этапе еще не создается.

Генерация, визуальная доводка и финальная редактура диаграмм выполняются
отдельным потоком. Отсутствие части диаграммных артефактов в `docs/diagrams/`
не блокирует подготовку реализации и не требует генерации диаграмм в рамках
данного этапа.

## 1. Цель этапа реализации

Цель этапа реализации — перейти от утвержденной проектной базы к сборке
рабочего full-stack приложения, в котором пользователь сможет вести личные
привычки, отмечать выполнение, смотреть прогресс, а администратор сможет
управлять состоянием учетных записей.

Реализация должна последовательно подтвердить ранее принятые документы:

- требования из `docs/requirements.md`;
- концептуальную архитектурную рамку из `docs/architecture-plan.md`;
- выбранный стек из `docs/stack-decision.md`;
- концептуальную модель данных из `docs/data-model.md`;
- предварительный API-план из `docs/api-plan.md`;
- проверки ролевой модели из `docs/role-model-validation.md`;
- планы тестирования и фаззинга из `docs/test-plan.md` и
  `docs/fuzzing-plan.md`;
- матрицу трассировки из `docs/traceability-matrix.md`.

Главный принцип этапа: не приписывать проекту функции, тесты, инфраструктуру
или свойства, которые еще не реализованы и не проверены.

## 2. Предлагаемая структура репозитория

Предлагаемая структура:

```text
.
├── backend/
│   ├── habittrack/
│   ├── apps/
│   │   ├── accounts/
│   │   ├── habits/
│   │   └── analytics/
│   ├── tests/
│   ├── fixtures/
│   ├── manage.py
│   ├── requirements.txt
│   └── Dockerfile
├── frontend/
│   ├── src/
│   │   ├── app/
│   │   ├── pages/
│   │   ├── features/
│   │   ├── shared/
│   │   └── api/
│   ├── public/
│   ├── package.json
│   ├── vite.config.ts
│   └── Dockerfile
├── docs/
│   ├── diagrams/
│   ├── implementation-plan.md
│   └── ...
├── infra/
│   ├── deploy/
│   └── notes/
├── .env.example
├── .gitignore
├── docker-compose.yml
└── README.md
```

Назначение ключевых частей:

| Путь | Назначение |
| --- | --- |
| `backend/` | Серверная часть на Django и Django REST Framework: модели, миграции, API, валидация, права доступа, тесты backend. |
| `backend/habittrack/` | Конфигурация Django-проекта: settings, urls, ASGI/WSGI, общие настройки окружения. |
| `backend/apps/accounts/` | Пользовательская модель, роли `user` / `admin`, статусы `active` / `blocked`, регистрация, вход, профиль и административные сценарии по учетным записям: список пользователей, просмотр статуса, блокировка и разблокировка. |
| `backend/apps/habits/` | Habit, HabitSchedule, HabitScheduleDay, HabitCompletion, CRUD привычек, архивирование и удаление, отметка выполнения, снятие ошибочной отметки и история выполнения. |
| `backend/apps/analytics/` | Расчет текущей серии, процента соблюдения, количества выполнений и данных общего дашборда. |
| `backend/tests/` | Интеграционные и API-тесты backend, включая проверки ролей и некорректных данных. |
| `backend/fixtures/` | Демонстрационные тестовые данные для пользователя, администратора, привычек и отметок. |
| `frontend/` | Клиентская часть на React, TypeScript и Vite. |
| `frontend/src/app/` | Инициализация приложения, роутинг, провайдеры состояния и общая сборка UI. |
| `frontend/src/pages/` | Страницы пользовательского и административного интерфейса. |
| `frontend/src/features/` | Функциональные блоки: auth, habits, analytics, admin. |
| `frontend/src/shared/` | Общие компоненты, утилиты, типы, обработка ошибок, базовые UI-элементы. |
| `frontend/src/api/` | Клиентские функции взаимодействия с backend API и обработка JWT. |
| `docs/` | Проектная документация, планы, отчетные материалы и доказательная база. |
| `docs/diagrams/` | Место хранения диаграммных артефактов, которые добавляются отдельным потоком. |
| `infra/` | Вспомогательные материалы для deploy и инфраструктурные заметки, не являющиеся кодом приложения. |
| `.env.example` | Шаблон переменных окружения для локального запуска и будущего deploy. |
| `docker-compose.yml` | Оркестрация локального запуска backend, frontend и PostgreSQL. |
| `README.md` | Описание проекта, структура, стек, запуск, тестирование и deploy-сведения. |

Dockerfile предлагается держать рядом с соответствующей частью приложения:
`backend/Dockerfile` и `frontend/Dockerfile`. Root-level `docker-compose.yml`
будет связывать сервисы и переменные окружения.

## 3. Порядок реализации по этапам

1. Инициализировать Git-репозиторий, если он еще не создан, и подготовить
   базовую структуру: `backend/`, `frontend/`, `infra/`, стартовый
   `README.md`, `.gitignore`, `.env.example`.
2. Инициализировать backend-каркас Django и Django REST Framework без
   предметной логики.
3. Подключить PostgreSQL и вынести конфигурацию в переменные окружения.
4. Добавить минимальный health-check endpoint для проверки запуска backend.
5. Реализовать в `accounts` пользовательскую модель, роли `user` / `admin` и
   статусы `active` / `blocked`.
6. Реализовать регистрацию, вход, JWT-аутентификацию, профиль и запрет
   пользовательских функций для заблокированной учетной записи.
7. Реализовать в `habits` модели и API для Habit, HabitSchedule и
   HabitScheduleDay.
8. Реализовать CRUD привычек, архивирование, возврат из архива и необратимое
   удаление с учетом владельца привычки.
9. Реализовать в `habits` HabitCompletion: отметка выполнения, снятие отметки,
   история, запрет дубликатов и запрет отметок в незапланированный день.
10. Реализовать в `analytics` расчет статистики: текущая серия, количество
    выполнений, процент соблюдения, общий дашборд.
11. Реализовать в `accounts` административный контур: список пользователей,
    просмотр статуса, блокировка и разблокировка учетной записи.
12. Инициализировать frontend-каркас React + TypeScript + Vite.
13. Реализовать пользовательские frontend-экраны: регистрация, вход, профиль,
    список привычек, форма привычки, детали, отметки, история и статистика.
14. Реализовать административный frontend-интерфейс: список пользователей,
    статус, блокировка и разблокировка.
15. Подготовить демонстрационные тестовые данные для пользовательского и
    административного сценариев.
16. Реализовать автоматизированные проверки MVP: auth, CRUD, отметки,
    статистика, admin-доступ, ролевые ограничения и некорректные роли.
17. Провести фаззинг-тестирование API и точек ввода, включая ролевую модель,
    даты, периодичность, идентификаторы и строки.
18. Подготовить Dockerfile для backend и frontend, root-level
    `docker-compose.yml`, инструкции запуска в README.
19. Подготовить облачный deploy и зафиксировать фактические параметры запуска.
20. Заполнить `docs/evidence-register.md` фактическими доказательствами:
    коммиты, результаты тестов, фаззинг, скриншоты, deploy, демонстрации
    пользовательских и административных сценариев.

## 4. Вертикальные инкременты

Реализацию предлагается вести десятью вертикальными инкрементами, чтобы после
каждого крупного шага проект оставался запускаемым и проверяемым.

### Инкремент 1. Репозиторный каркас

Результат:

- создана базовая структура `backend/`, `frontend/`, `infra/`;
- добавлены стартовый `README.md`, `.gitignore`, `.env.example`;
- структура не содержит бизнес-логики и не заявляет еще не реализованные
  возможности.

Проверка:

- структура читается из README;
- нет преждевременных Docker, Django или React артефактов, если они еще не
  инициализированы.

### Инкремент 2. Backend foundation

Результат:

- backend запускается локально;
- подключены Django, DRF и PostgreSQL;
- конфигурация берется из окружения;
- есть health-check endpoint;
- выполнение миграций намеренно отложено до Инкремента 3, чтобы сначала
  создать `accounts.User` и задать `AUTH_USER_MODEL`.

Проверка:

- backend проверяется через `manage.py check`;
- health-check возвращает успешный ответ;
- приложение настроено на PostgreSQL через переменные окружения;
- миграции не запускаются до появления кастомной пользовательской модели.

### Инкремент 3. Accounts, roles and auth

Результат:

- реализована учетная запись с ролью и статусом;
- работают регистрация, вход, JWT и профиль;
- обычный пользователь не может назначить себе `admin`;
- заблокированный пользователь не получает доступ к пользовательским функциям.

Проверка:

- API-тесты регистрации, входа и профиля проходят;
- невалидные роли и попытки подмены роли отклоняются;
- сценарии из `docs/role-model-validation.md` начинают закрываться тестами.

### Инкремент 4. Habits and schedules

Результат:

- реализованы Habit, HabitSchedule и HabitScheduleDay;
- пользователь может создавать, читать, редактировать и удалять свои привычки;
- поддержаны ежедневная периодичность и выбранные дни недели;
- пользователь не получает доступ к чужим привычкам.

Проверка:

- CRUD-тесты привычек проходят;
- проверяется владелец привычки;
- отклоняются некорректные режимы периодичности и дни недели.

### Инкремент 5. Completions and history

Результат:

- пользователь может отметить выполнение привычки за дату;
- пользователь может снять ошибочную отметку;
- история выполнения доступна по привычке;
- backend запрещает дубликаты и отметки в незапланированные дни.

Проверка:

- тесты отметок выполнения проходят;
- проверяются чужие привычки, дубликаты, невалидные даты и расписание.

### Инкремент 6. Statistics and dashboard API

Результат:

- рассчитывается текущая серия с учетом расписания;
- рассчитываются количество выполнений и процент соблюдения;
- доступен общий пользовательский дашборд.

Проверка:

- тесты статистики покрывают ежедневные привычки и привычки по дням недели;
- процент соблюдения считается по запланированным датам;
- статистика чужих привычек недоступна.

### Инкремент 7. Admin contour

Результат:

- администратор видит список пользователей и статусы учетных записей;
- администратор может блокировать и разблокировать пользователей;
- неавторизованный и обычный пользователь не получают admin-доступ.

Проверка:

- тесты admin API проходят;
- ролевые проверки из `docs/role-model-validation.md` закрыты;
- невалидные значения роли и статуса отклоняются.

### Инкремент 8. Frontend user flow

Результат:

- реализованы регистрация, вход и профиль;
- реализованы список привычек, создание и редактирование привычек;
- реализованы отметка выполнения, история, статистика и дашборд.

Проверка:

- пользовательский сценарий проходит через UI от входа до статистики;
- frontend корректно обрабатывает ошибки доступа и ошибки валидации.

### Инкремент 9. Admin UI and demo data

Результат:

- реализован административный интерфейс;
- администратор видит список пользователей и статусы учетных записей;
- администратор может блокировать и разблокировать пользователей;
- подготовлены демонстрационные данные;
- готов demo-сценарий для защиты.

Проверка:

- административный сценарий проходит через UI;
- demo-данные покрывают обычного пользователя, администратора, привычки,
  отметки и состояние учетной записи.

### Инкремент 10. Quality, packaging and delivery

Результат:

- выполнены автоматизированные проверки;
- проведено фаззинг-тестирование;
- подготовлены Dockerfile, Docker Compose, README и deploy;
- доказательства занесены в `docs/evidence-register.md`.

Проверка:

- тесты и фаззинг имеют сохраненные результаты;
- приложение запускается по README и через Docker/compose.

## 5. Git-стратегия

Работу нужно вести через последовательные осмысленные коммиты, а не через один
крупный финальный коммит. Предлагаемый стиль сообщений — Conventional Commits
на английском языке.

Рекомендуемая логика:

- один коммит на крупный технический шаг или завершенный вертикальный кусок;
- коммитить только согласованное состояние, которое можно объяснить и
  проверить;
- перед коммитом запускать доступные проверки для затронутой части;
- не смешивать документацию, backend, frontend и инфраструктуру в одном
  коммите без необходимости;
- после появления фактических доказательств обновлять
  `docs/evidence-register.md` отдельным `docs:`-коммитом или вместе с
  соответствующим проверенным этапом.

Примеры сообщений:

```text
chore: scaffold repository structure
feat(backend): add django health check and database config
feat(auth): add jwt authentication and account profile
feat(habits): add habit schedule CRUD
feat(habits): add completion history workflow
feat(analytics): add streak and compliance calculations
feat(accounts): add admin account management API
feat(frontend): add user habit dashboard
feat(frontend): add admin user management screen
test(api): cover role validation scenarios
test(fuzzing): add invalid input fuzzing checks
chore(docker): add compose setup
docs: update evidence register
```

## 6. Первый кодовый ход после утверждения плана

После подтверждения этого плана первым кодовым ходом должно быть создание
минимального репозиторного каркаса без бизнес-логики:

1. Создать директории `backend/`, `frontend/`, `infra/`.
2. Добавить стартовый `README.md` с кратким описанием HabitTrack,
   утвержденным стеком, будущей структурой и пометкой, что реализация идет
   инкрементально.
3. Добавить стартовый `.gitignore` для Python, Django, Node/Vite, окружений,
   логов и локальных файлов.
4. Добавить `.env.example` с будущими переменными окружения без секретов.
5. При необходимости добавить placeholder-файлы в пустые директории, чтобы
   структура фиксировалась в Git.
6. Проверить состояние Git и подготовить первый осмысленный коммит после
   подтверждения состава файлов.

В этот первый кодовый ход не входят:

- инициализация Django;
- инициализация React/Vite;
- создание `docker-compose.yml`;
- создание Dockerfile;
- реализация моделей, API, UI или бизнес-логики;
- создание или редактирование диаграммных артефактов.

## 7. Спорные места перед началом реализации

Перед стартом кода стоит явно принять несколько небольших решений:

| Вопрос | Предлагаемое решение |
| --- | --- |
| Где хранить Dockerfile? | Держать `backend/Dockerfile` и `frontend/Dockerfile`, а `docker-compose.yml` — в корне. |
| Где хранить deploy-материалы? | Использовать `infra/` для заметок, конфигураций и материалов deploy, не смешивая их с кодом приложения. |
| Какой стиль коммитов использовать? | Conventional Commits на английском языке. |
| Что делать, если Git еще не инициализирован? | Выполнить `git init` перед первым коммитом или подключить существующий удаленный репозиторий. |
| Как создать первого администратора? | На этапе backend auth выбрать проверяемый способ: fixture, management command или ручное создание через Django admin/shell. |
| Когда обновлять доказательную базу? | Только после появления фактических артефактов: тестов, скриншотов, deploy, GitHub-ссылок, результатов фаззинга. |
| Что делать с диаграммами? | Не генерировать и не редактировать их в реализации; диаграммный пакет добавляется отдельно. |
