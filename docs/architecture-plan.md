# План архитектуры

## Статус

Сформирована концептуальная архитектурная рамка HabitTrack и зафиксировано
утвержденное технологическое направление. На этом этапе не проектируются
конкретная схема базы данных, API-контракты, структура таблиц и детали
реализации.

## 1. Архитектурная рамка

Для HabitTrack подходит клиент-серверная веб-архитектура, потому что продукт
работает с персональными учетными записями, накопительной историей привычек,
разграничением ролей и удаленным доступом пользователя к своим данным.
Привычки, отметки выполнения и статистика должны сохраняться между сеансами
работы, а пользователь должен иметь возможность войти в систему и продолжить
работу с актуальным состоянием привычек.

На уровне продукта система должна состоять из следующих крупных частей:

- клиентский веб-интерфейс для работы пользователя и администратора с
  доступными сценариями;
- серверная часть с прикладной логикой, проверками доступа, правилами работы с
  привычками, расчетом статистики и обработкой административных действий;
- хранилище данных для учетных записей, привычек, периодичности, отметок,
  истории, статистически значимых данных и состояния аккаунтов;
- служебный административный контур для просмотра пользователей, статусов
  учетных записей, блокировки и разблокировки аккаунтов;
- механизм конфигурации и развертывания, который на следующих этапах будет
  связан с методологией двенадцати факторов, воспроизводимым запуском,
  Docker/README и облачным deploy.

Клиентская часть должна отвечать за взаимодействие пользователя с системой и
передачу пользовательских действий в серверную часть. Серверная часть должна
быть местом применения предметных правил: доступ к личным данным, расчет
серии, процент соблюдения, архивирование, необратимое удаление, блокировка
пользователя и проверка роли. Хранилище данных должно обеспечивать сохранение
накопительной истории и возможность восстановления состояния после повторного
входа.

## 2. Основные функциональные контуры

### Аутентификация и профиль

Контур отвечает за регистрацию, вход, завершение сеанса, просмотр и
редактирование базового профиля. Он также должен учитывать состояние учетной
записи: заблокированный пользователь не должен получать доступ к
пользовательским функциям.

Связанные требования: FR-01, FR-02, FR-03, NFR-01, NFR-02.

### Работа с привычками

Контур отвечает за создание, просмотр, редактирование и удаление привычек, а
также за указание цели или причины привычки. Обычный пользователь должен
работать только со своими привычками.

Связанные требования: FR-04, FR-05, FR-06, FR-07, FR-08, FR-09, FR-17.

### Периодичность и отметки выполнения

Контур отвечает за настройку периодичности привычки и фиксацию выполнения за
конкретную дату. Периодичность должна влиять на дальнейший расчет серии и
процента соблюдения.

Связанные требования: FR-10, FR-11, NFR-02.

### История и статистика

Контур отвечает за просмотр истории выполнения, расчет текущей серии, базовой
статистики и общего дашборда. Статистика должна отражать предметную
регулярность, а не просто количество календарных дней.

Связанные требования: FR-12, FR-13, FR-14, FR-15, NFR-03, NFR-04.

### Архивирование и удаление

Контур отвечает за разделение активных и архивных привычек, возврат привычки
из архива и необратимое удаление привычки. Архивирование сохраняет историю,
удаление является отдельным осознанным действием и удаляет связанные данные.

Связанные требования: FR-09, FR-16, NFR-03.

### Административное управление пользователями и ролями

Контур отвечает за административный вход, просмотр пользователей, просмотр
статуса учетной записи, блокировку и разблокировку аккаунта, а также запрет
административных функций для обычных и неавторизованных пользователей.

Связанные требования: FR-18, FR-19, FR-20, FR-21, FR-22, NFR-01, NFR-02,
NFR-08.

## 3. Ключевые предметные правила

При дальнейшем проектировании необходимо учитывать следующие правила:

- серия выполнения должна учитывать периодичность привычки, а не просто
  календарные дни подряд;
- процент соблюдения должен рассчитываться относительно запланированных дат
  выполнения;
- процент соблюдения в MVP рассчитывается за весь период отслеживания привычки:
  для активной привычки от даты создания до текущей даты, для архивной — от
  даты создания до даты архивирования;
- отметка выполнения в незапланированный день в MVP запрещена;
- архивирование не удаляет историю выполнения привычки;
- удаление необратимо удаляет привычку и связанные с ней данные;
- заблокированный пользователь не должен получать доступ к пользовательским
  функциям;
- обычный пользователь не должен иметь доступ к привычкам других пользователей;
- обычный пользователь не должен иметь доступ к административным функциям;
- неавторизованный пользователь не должен иметь доступ к пользовательским и
  административным функциям;
- невалидные значения роли должны отклоняться;
- попытки несанкционированного получения административного доступа должны
  отклоняться;
- основные точки ввода должны быть пригодны для последующего тестирования и
  фаззинг-тестирования.

## 4. Сценарии для дальнейших диаграмм

В следующих диаграммах должны быть хорошо видны такие сценарии:

- регистрация и вход пользователя;
- создание привычки;
- настройка периодичности привычки;
- отметка выполнения привычки за дату;
- просмотр истории и статистики;
- архивирование привычки;
- необратимое удаление привычки;
- блокировка пользователя администратором;
- попытка доступа к административной функции без нужной роли;
- отклонение невалидного значения роли.

## 5. Ограничения текущего архитектурного этапа

Этот документ фиксирует концептуальную архитектурную рамку, предметные правила
и утвержденное технологическое направление. Он пока не является проектом базы
данных, описанием API или финальной схемой развертывания.

## 6. Утвержденное технологическое направление

Для дальнейшего проектирования HabitTrack принято следующее технологическое
направление:

- backend: Python, Django, Django REST Framework;
- frontend: React, TypeScript, Vite;
- база данных: PostgreSQL;
- аутентификация клиент-серверного взаимодействия: JWT;
- инженерная упаковка: Dockerfile, docker-compose, `.env.example`,
  конфигурация через переменные окружения;
- облачное развертывание: конкретная платформа выбирается позже на этапе
  deploy.

Выбранное направление соответствует ранее зафиксированной клиент-серверной
рамке:

- React + TypeScript + Vite покрывают клиентский веб-интерфейс и позволяют
  реализовать сценарии пользователя и администратора в браузере;
- Django + Django REST Framework покрывают серверную часть с прикладной
  логикой, проверками доступа, ролевыми ограничениями, обработкой привычек,
  отметок, статистики и административных действий;
- PostgreSQL покрывает потребность в надежном хранении учетных записей,
  привычек, отметок выполнения, истории и состояния аккаунтов;
- JWT используется как механизм аутентифицированного взаимодействия клиента с
  серверной частью;
- Dockerfile, docker-compose и конфигурация через окружение поддерживают
  воспроизводимость запуска, подготовку к облачному deploy и будущую связь с
  методологией двенадцати факторов.

Это решение фиксирует технологическое направление, но не определяет схему БД,
API-контракты, конкретные маршруты взаимодействия, структуру компонентов
frontend или детальную инфраструктуру deploy.
