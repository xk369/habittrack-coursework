# Валидация ролевой модели

## 1. Назначение документа

Документ фиксирует проверочную спецификацию ролевой модели и auth-доступов
HabitTrack. Он нужен для того, чтобы реализация аккаунтов, ролей, статусов и
профиля проверялась не только вручную, но и через воспроизводимые API-тесты.

Спецификация используется как источник для:

- реализации auth/account backend-контура;
- API-тестов Инкрементов 3 и 7;
- ревью запретов на подмену роли и статуса;
- ревью административного контура и сценариев блокировки учетных записей.

## 2. Проверяемые правила

- допустимые роли пользователя: `user`, `admin`;
- допустимые статусы учетной записи: `active`, `blocked`;
- пользователь не может задать `role` или `status` через регистрацию;
- пользователь не может изменить `role` или `status` через профиль;
- заблокированный пользователь не получает доступ к пользовательским
  функциям;
- анонимный пользователь не получает доступ к защищенным endpoint;
- административные endpoint доступны только активному пользователю с
  `role=admin`;
- обычный активный пользователь не получает доступ к admin endpoint;
- заблокированный admin не получает доступ к admin endpoint;
- блокировка синхронизирует `status=blocked` и `is_active=False`;
- разблокировка синхронизирует `status=active` и `is_active=True`;
- admin не может заблокировать собственную учетную запись;
- refresh token после блокировки не должен выдавать новый access token.

## 3. Фактические admin endpoint

- `GET /api/admin/users/` — список пользователей;
- `GET /api/admin/users/{user_id}/` — данные пользователя;
- `POST /api/admin/users/{user_id}/block/` — блокировка пользователя;
- `POST /api/admin/users/{user_id}/unblock/` — разблокировка пользователя.

## 4. Матрица доступа

| Субъект | Auth/profile/habits/completions/statistics | Admin API |
| --- | --- | --- |
| Anonymous | Нет доступа к защищенным endpoint. | Нет доступа. |
| `user`, `active` | Доступ только к собственным пользовательским данным. | Нет доступа. |
| `user`, `blocked` | Нет доступа к пользовательским функциям. | Нет доступа. |
| `admin`, `active` | Доступ как активный пользователь и доступ к admin API. | Есть доступ. |
| `admin`, `blocked` | Нет доступа к пользовательским функциям. | Нет доступа. |

MVP-ограничение по JWT: уже выданный access token может оставаться формально
валидным до окончания TTL, но каждый защищенный endpoint проверяет актуальный
`status` пользователя через permission. JWT-authentication намеренно не
отсеивает blocked-user по `is_active` на этапе проверки access token: бизнес-
проверка остается в `IsAuthenticatedAndActive`, поэтому protected endpoints
возвращают 403 для blocked-user. Refresh после блокировки запрещен кастомным
refresh serializer.

## 6. Статус

Документ подготовлен как спецификация для реализации и тестирования
Инкрементов 3 и 7. Фактические результаты тестов фиксируются после запуска
проверок и используются для ревью реализации auth/admin-контура.
