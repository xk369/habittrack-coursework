# Валидация ролевой модели

## 1. Назначение документа

Документ фиксирует проверочную спецификацию ролевой модели и auth-доступов
HabitTrack. Он нужен для того, чтобы реализация аккаунтов, ролей, статусов и
профиля проверялась не только вручную, но и через воспроизводимые API-тесты.

Спецификация используется как источник для:

- реализации auth/account backend-контура;
- API-тестов Инкремента 3;
- ревью запретов на подмену роли и статуса;
- дальнейшего расширения admin-контура без пересмотра базовых правил.

## 2. Проверяемые правила

- допустимые роли пользователя: `user`, `admin`;
- допустимые статусы учетной записи: `active`, `blocked`;
- пользователь не может задать `role` или `status` через регистрацию;
- пользователь не может изменить `role` или `status` через профиль;
- заблокированный пользователь не получает доступ к пользовательским
  функциям;
- анонимный пользователь не получает доступ к защищенным endpoint;
- admin-доступ в Инкременте 3 не реализуется, но роль `admin` уже должна
  существовать на уровне модели для будущего административного контура.

## 3. Сценарии валидации

| ID | Цель | Входные данные / предусловия | Ожидаемый результат | Подтверждает |
| --- | --- | --- | --- | --- |
| RM-01 | Проверить успешную регистрацию обычного пользователя. | `POST /api/auth/register/` с валидными `email`, `password`, `display_name`. | Создан пользователь с `role=user`, `status=active`; возвращены данные аккаунта без пароля. | FR-01, FR-22, NFR-01, NFR-02. |
| RM-02 | Запретить назначение admin-роли при регистрации. | `POST /api/auth/register/` с `role=admin`. | Запрос отклонен ошибкой валидации; пользователь не создан. | FR-22, NFR-01, NFR-02. |
| RM-03 | Запретить назначение статуса при регистрации. | `POST /api/auth/register/` с `status=blocked` или другим `status`. | Запрос отклонен ошибкой валидации; пользователь не создан. | FR-22, NFR-01, NFR-02. |
| RM-04 | Проверить валидацию email при регистрации. | `POST /api/auth/register/` с невалидным email. | Запрос отклонен ошибкой валидации. | FR-01, NFR-02. |
| RM-05 | Проверить валидацию пароля при регистрации. | `POST /api/auth/register/` с пустым или слабым паролем. | Запрос отклонен правилами валидации пароля. | FR-01, NFR-02. |
| RM-06 | Проверить успешный вход активного пользователя. | Существует пользователь `status=active`; `POST /api/auth/login/` с корректными credentials. | Возвращены JWT access и refresh tokens. | FR-02, NFR-01. |
| RM-07 | Запретить вход заблокированному пользователю. | Существует пользователь `status=blocked`; `POST /api/auth/login/` с корректными credentials. | Запрос отклонен; JWT-токены не выдаются. | FR-02, FR-20, NFR-01. |
| RM-08 | Отклонить неверные credentials. | `POST /api/auth/login/` с неверным email или password. | Запрос отклонен; JWT-токены не выдаются. | FR-02, NFR-01. |
| RM-09 | Разрешить доступ к профилю активному авторизованному пользователю. | Активный пользователь отправляет `GET /api/account/profile/` с валидным JWT. | Возвращены данные собственного профиля. | FR-03, NFR-01. |
| RM-10 | Запретить доступ к профилю анонимному пользователю. | `GET /api/account/profile/` без JWT. | Запрос отклонен как неавторизованный. | FR-03, NFR-01. |
| RM-11 | Запретить доступ к профилю заблокированному пользователю. | Заблокированный пользователь отправляет `GET /api/account/profile/` с JWT. | Запрос отклонен из-за статуса учетной записи. | FR-03, FR-20, NFR-01. |
| RM-12 | Разрешить изменение допустимого профильного поля. | Активный пользователь отправляет `PATCH /api/account/profile/` с `display_name`. | Поле профиля обновлено; роль и статус не меняются. | FR-03, NFR-02. |
| RM-13 | Запретить изменение роли через профиль. | Активный пользователь отправляет `PATCH /api/account/profile/` с `role=admin`. | Запрос отклонен ошибкой валидации; роль не изменена. | FR-22, NFR-01, NFR-02. |
| RM-14 | Запретить изменение статуса через профиль. | Активный пользователь отправляет `PATCH /api/account/profile/` с `status=blocked` или другим `status`. | Запрос отклонен ошибкой валидации; статус не изменен. | FR-22, NFR-01, NFR-02. |
| RM-15 | Зафиксировать готовность роли `admin` на уровне модели. | Создание пользователя с ролью `admin` через служебный backend-механизм. | Роль существует как допустимое значение модели; пользовательский ввод не может назначить ее себе. | FR-18, FR-21, FR-22. |
| RM-16 | Зафиксировать готовность статуса `blocked` на уровне модели. | Создание или изменение пользователя со статусом `blocked` через служебный backend-механизм. | Статус существует как допустимое значение модели; заблокированный пользователь не получает пользовательский доступ. | FR-20, FR-21, FR-22. |
| RM-17 | Не заявлять admin API как готовый в Инкременте 3. | Проверка состава реализованных endpoint. | Admin API отсутствует; готова только модель ролей для будущего admin-контура. | FR-18-FR-22, NFR-01. |

## 4. Статус

Документ подготовлен как спецификация для реализации и тестирования
Инкремента 3. Фактические результаты тестов будут добавляться после реализации
и запуска проверок.
