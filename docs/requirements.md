# Требования

## Статус

Сформулированы функциональные и нефункциональные требования к MVP на основе
утвержденного product brief, анализа предметной области, проблем P1-P7, анализа
аналогов и обязательств листа задания. На этом этапе не выбираются стек,
архитектура, база данных, API, диаграммы и реализация.

## 1. Функциональные требования

| ID | Формулировка требования | Обоснование / связь |
| --- | --- | --- |
| FR-01 | Система должна позволять новому пользователю зарегистрировать учетную запись. | Необходимо для личного пространства пользователя и перехода от ручного учета к веб-сервису; связано с P5 и заданием на авторизацию/аутентификацию. |
| FR-02 | Система должна позволять зарегистрированному пользователю входить в систему и завершать сеанс работы. | Нужно для доступа к личным привычкам и защиты пользовательских данных; связано с P5, P7 и заданием. |
| FR-03 | Система должна позволять пользователю просматривать и редактировать базовые сведения личного профиля. | Поддерживает личное пространство пользователя и учетную запись как часть автоматизации; связано с P5. |
| FR-04 | Система должна позволять пользователю создавать привычку. | Базовое действие предметной области; связано с P1, P3 и задачей CRUD-приложения. |
| FR-05 | Система должна позволять пользователю указывать для привычки краткую цель или причину. | Помогает связать повторяющееся действие с намерением пользователя; вытекает из product brief и усиливает предметную логику формирования привычек. |
| FR-06 | Система должна позволять пользователю просматривать список своих привычек. | Нужен единый цифровой список привычек вместо фрагментации между памятью, бумагой и таблицами; связано с P5. |
| FR-07 | Система должна позволять пользователю просматривать подробную информацию по выбранной привычке. | Нужно для доступа к цели, периодичности, состоянию и дальнейшему просмотру истории; связано с P2-P4. |
| FR-08 | Система должна позволять пользователю редактировать сведения о привычке. | Требуется для полноценного CRUD и изменения намерения или параметров привычки без создания новой записи; связано с заданием. |
| FR-09 | Система должна позволять пользователю выполнить явное необратимое удаление привычки вместе со связанными с ней данными. | Требуется для CRUD-сценариев. Удаление является отдельным осознанным действием и не заменяет архивирование, которое используется для скрытия привычки из активного списка без потери истории. |
| FR-10 | Система должна позволять пользователю настраивать периодичность привычки: ежедневно или по выбранным дням недели. | Прямо решает проблему слабой поддержки периодичности; связано с P3 и выводами анализа аналогов. |
| FR-11 | Система должна позволять пользователю отмечать выполнение привычки за конкретную дату и корректировать такую отметку при ошибке. | Решает проблему надежной фиксации выполнения и неточных отметок задним числом; связано с P1 и P2. |
| FR-12 | Система должна позволять пользователю просматривать историю выполнения привычки по датам. | Решает проблему невозможности достоверно восстановить историю; связано с P2 и выводами по аналогам. |
| FR-13 | Система должна рассчитывать и отображать текущую серию выполнения привычки. | Дает пользователю понятный показатель регулярности; связано с P4 и практиками habit tracker. |
| FR-14 | Система должна рассчитывать и отображать базовую статистику по привычке: количество выполнений и процент соблюдения. | Делает прогресс объективным, а не субъективным; связано с P4. |
| FR-15 | Система должна предоставлять общий дашборд прогресса по привычкам пользователя. | Позволяет видеть целостную картину вместо разрозненных записей; связано с P4 и P5. |
| FR-16 | Система должна позволять архивировать привычку и возвращать ее из архива без потери истории выполнения. | Решает проблему смешивания активных и неактуальных привычек и потери истории; связано с P6 и выводами по Habitify. |
| FR-17 | Система должна ограничивать обычного пользователя работой только со своими привычками и личной историей. | Нужно для личного веб-сервиса и контролируемого доступа; связано с P5 и P7. |
| FR-18 | Система должна поддерживать вход пользователя с административной ролью. | Требуется для служебных административных сценариев и проверки ролевой модели по заданию; связано с P7. |
| FR-19 | Система должна позволять администратору просматривать список пользователей и статус каждой учетной записи. | Поддерживает управление учетными записями; связано с P7 и product brief. |
| FR-20 | Система должна позволять администратору блокировать и разблокировать учетную запись пользователя. | Является достаточным административным действием для текущего MVP; связано с P7. |
| FR-21 | Система должна запрещать доступ к административным функциям неавторизованным пользователям и обычным пользователям. | Обязательное требование ролевого разграничения; связано с P7 и заданием. |
| FR-22 | Система должна отклонять некорректные значения роли и попытки несанкционированного получения административного доступа. | Прямо покрывает требование задания о валидации ролевой модели на некорректные данные; связано с P7. |
| FR-23 | Система должна содержать демонстрационные тестовые данные для показа основных пользовательских и административных сценариев. | Требуется листом задания для проверки работоспособности и демонстрации продукта. |

## 2. Нефункциональные требования

| ID | Формулировка требования | Обоснование / связь |
| --- | --- | --- |
| NFR-01 | Доступ к пользовательским и административным действиям должен разграничиваться по роли и состоянию учетной записи. | Поддерживает безопасность доступа и проверяемость P7. |
| NFR-02 | Входные данные должны валидироваться с понятным отклонением некорректных значений. | Нужно для корректной работы с привычками, периодичностью, отметками и ролями; связано с P1-P4 и P7. |
| NFR-03 | История выполнения привычки должна сохраняться при обычном просмотре, редактировании и архивировании привычки; требование не распространяется на явное необратимое удаление пользователем. | Поддерживает сохранность пользовательской истории при штатной работе с привычкой и не конфликтует с отдельным сценарием удаления; связано с P2 и P6. |
| NFR-04 | Основные пользовательские сценарии должны быть доступны через веб-интерфейс без необходимости использовать внешние таблицы, заметки или ручные расчеты. | Поддерживает удобство базовых сценариев и решает P5. |
| NFR-05 | Система должна быть доступна пользователю как веб-приложение после входа в учетную запись. | Соответствует теме клиент-серверного приложения и product brief, не фиксируя конкретный стек. |
| NFR-06 | Развертывание проекта должно быть воспроизводимым для локальной проверки и облачной демонстрации. | Связано с обязательствами по Docker, README и deploy. |
| NFR-07 | Конфигурация окружения должна задаваться вне исходного кода через параметры окружения или эквивалентный механизм. | Закладывает будущую связь с методологией двенадцати факторов без выбора реализации. |
| NFR-08 | Основные точки ввода должны быть пригодны для автоматизированного тестирования и фаззинг-тестирования. | Поддерживает обязательное фаззинг-тестирование и проверку некорректных данных ролевой модели. |

## 3. Ограничения текущего этапа

Требования фиксируют, что должна делать система и какими свойствами она должна
обладать. Они не задают программный стек, архитектурный стиль, структуру базы
данных, API-контракты, конкретный интерфейс или способ реализации.
