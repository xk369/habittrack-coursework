# Обоснование технологического стека

## Статус

Зафиксировано утвержденное технологическое направление для реализации
HabitTrack. Документ объясняет выбор стека, но не проектирует базу данных, API,
диаграммы, структуру кода или конкретную инфраструктуру deploy.

## 1. Выбранный стек

Backend:

- Python;
- Django;
- Django REST Framework.

Frontend:

- React;
- TypeScript;
- Vite.

База данных:

- PostgreSQL.

Инженерная упаковка и развертывание:

- Dockerfile;
- docker-compose для локального запуска;
- конфигурация через переменные окружения;
- `.env.example`;
- JWT-аутентификация для клиент-серверного взаимодействия;
- облачный deploy на подходящей платформе, которая будет выбрана позже.

## 2. Почему Django + Django REST Framework

Django подходит для HabitTrack, потому что проект требует надежной серверной
части с учетными записями, ролями, проверками доступа, CRUD-сценариями,
валидацией данных и работой с persistent-хранилищем. Для курсовой работы важно
получить не только набор отдельных точек взаимодействия, а целостную серверную
платформу, где можно последовательно реализовать прикладную логику и проверить
ее тестами.

Django REST Framework дополняет Django как инструмент для построения
клиент-серверного взаимодействия. Он подходит для разделения frontend и
backend, реализации сериализации данных, валидации входных значений,
ограничения доступа и последующего тестирования точек ввода.

Для HabitTrack это особенно важно, потому что серверная часть должна
контролировать:

- регистрацию и вход;
- профиль пользователя;
- принадлежность привычек конкретному пользователю;
- создание, изменение, архивирование и удаление привычек;
- отметки выполнения по датам;
- расчет статистики с учетом периодичности;
- административные действия;
- запрет доступа без нужной роли;
- отклонение некорректных значений роли.

## 3. Почему React + TypeScript + Vite

React подходит для HabitTrack как основа клиентского веб-интерфейса, потому
что приложение предполагает несколько связанных пользовательских состояний:
текущая учетная запись, список привычек, выбранная привычка, отметки,
статистика, архив и административный раздел.

TypeScript выбран для повышения надежности клиентской части. Он помогает
явнее описывать формы данных, свойства компонентов и обработку состояний, что
важно для сценариев с привычками, отметками, ролями и ошибками валидации.

Vite выбран как современный инструмент сборки frontend-приложения. Он
подходит для учебного full-stack проекта, потому что упрощает локальную
разработку, сборку клиентской части и дальнейшую интеграцию с Docker/deploy.

В контексте HabitTrack этот стек позволяет реализовать:

- регистрацию и вход через веб-интерфейс;
- формы создания и редактирования привычек;
- выбор периодичности;
- отметку выполнения;
- просмотр истории и статистики;
- общий дашборд;
- административный экран пользователей;
- отображение ошибок доступа и ошибок валидации.

## 4. Почему PostgreSQL

Методические указания допускают и приветствуют NoSQL-подход, однако для
HabitTrack выбран PostgreSQL, потому что предметная область имеет
структурированные данные и выраженные связи:

- пользователь владеет привычками;
- привычка имеет периодичность и состояние;
- привычка имеет отметки выполнения по датам;
- статистика рассчитывается на основе истории отметок;
- учетная запись имеет роль и статус.

Для этих данных важны целостность, связи между сущностями, ограничения,
надежное хранение истории и понятная проверка корректности. PostgreSQL хорошо
подходит для такой модели, потому что позволяет хранить структурированные
записи, поддерживать связи и обеспечивать предсказуемость данных.

Выбор SQL-СУБД обоснован тем, что MVP не требует свободной документной схемы
или хранения слабоструктурированных событий. Напротив, проекту нужны
однозначные сущности и связи, которые позже будут отражены в ER-диаграмме.

## 5. Почему стек подходит именно для HabitTrack

HabitTrack требует полного клиент-серверного цикла:

- пользователь работает в браузере;
- сервер применяет предметные правила;
- данные сохраняются между сеансами;
- роль администратора отделена от роли пользователя;
- история выполнения привычек не теряется при штатных действиях;
- статистика рассчитывается на основе сохраненных отметок;
- некорректные значения роли и попытки обхода доступа отклоняются.

Выбранный стек поддерживает эту модель без избыточной сложности:

- React + TypeScript + Vite закрывают пользовательский и административный
  веб-интерфейс;
- Django + DRF закрывают серверную прикладную логику, валидацию и доступ;
- PostgreSQL закрывает долговременное структурированное хранение данных;
- JWT закрывает сценарий клиент-серверной аутентификации;
- Docker/docker-compose поддерживают воспроизводимый запуск;
- переменные окружения и `.env.example` поддерживают будущую связь с
  12-factor.

## 6. Связь с требованиями

### Роли и доступ

Django + DRF подходят для реализации ролевых ограничений, запрета доступа к
чужим привычкам, проверки административных действий и отклонения некорректных
значений роли.

Связанные требования: FR-17, FR-18, FR-19, FR-20, FR-21, FR-22, NFR-01,
NFR-02.

### История и статистика

PostgreSQL и серверная прикладная логика подходят для хранения отметок
выполнения, восстановления истории, расчета серии и процента соблюдения с
учетом периодичности привычки.

Связанные требования: FR-10, FR-11, FR-12, FR-13, FR-14, FR-15, FR-16,
NFR-03.

### Тестирование и фаззинг

Разделение frontend и backend, серверная валидация и явные точки ввода
позволяют подготовить автоматизированные проверки и фаззинг-тестирование
сценариев регистрации, привычек, отметок, ролей и административного доступа.

Связанные требования: FR-22, NFR-02, NFR-08.

### Docker/deploy и 12-factor

Dockerfile, docker-compose, `.env.example` и конфигурация через переменные
окружения позволяют подготовить воспроизводимый запуск и дальнейшее облачное
развертывание. Это напрямую связано с инженерной частью задания и принципами
двенадцати факторов.

Связанные требования: NFR-06, NFR-07.

## 7. Что пока не фиксируется

На этом этапе не фиксируются:

- структура базы данных;
- ER-диаграмма;
- API-контракты и конкретные маршруты взаимодействия;
- структура frontend-компонентов;
- структура Django-приложений;
- конкретные библиотеки JWT;
- конкретные библиотеки тестирования и фаззинга;
- облачная платформа;
- CI/CD;
- production-настройки.

Эти решения принимаются на следующих этапах после утверждения стека.
