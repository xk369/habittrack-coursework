# Предварительный API-план

## Статус

Документ фиксирует API-план на уровне ресурсов, сценариев, требований,
проверок доступа и будущих направлений валидации/фаззинга. Здесь не задаются
точные URL, HTTP-коды, сериализаторы, поля request/response, конкретные
библиотеки JWT и OpenAPI-схема.

## 1. Общие принципы API

API должен поддерживать разделение клиентского веб-интерфейса и серверной
прикладной логики. Серверная часть должна быть источником проверки доступа,
валидации входных данных и применения предметных правил.

Общие правила:

- пользовательские операции требуют аутентификации;
- заблокированный пользователь не должен выполнять пользовательские операции;
- обычный пользователь работает только со своими привычками и отметками;
- административные операции доступны только пользователю с корректной
  административной ролью;
- невалидные роли, статусы, даты, периодичность и попытки доступа к чужим
  данным должны отклоняться;
- роль поддерживает только значения `user` и `admin`;
- статус учетной записи поддерживает только значения `active` и `blocked`;
- отметка выполнения разрешена только за дату, соответствующую расписанию
  привычки;
- основные точки ввода должны быть пригодны для последующего
  фаззинг-тестирования.

## 2. Auth / account

### Назначение

Контур отвечает за регистрацию, вход, завершение сеанса, просмотр профиля и
обновление профиля.

### Сценарии

- регистрация нового пользователя;
- вход пользователя;
- завершение сеанса или сценарий выхода на стороне клиента/сервера;
- просмотр текущего профиля;
- обновление базовых сведений профиля.

### Закрываемые требования

- FR-01;
- FR-02;
- FR-03;
- FR-17;
- NFR-01;
- NFR-02;
- NFR-05;
- NFR-08.

### Обязательные проверки доступа

- неавторизованный пользователь не должен получать профиль;
- заблокированный пользователь не должен получать доступ к пользовательским
  функциям;
- пользователь не должен иметь возможность назначать себе административную роль
  через регистрацию или обновление профиля;
- пользователь не должен иметь возможность менять свой account status через
  профиль.

### Невалидные данные для будущей валидации и фаззинга

- пустые или слишком длинные значения полей регистрации;
- некорректный формат данных для входа;
- повторная регистрация с уже занятыми учетными данными;
- попытка передать роль при регистрации;
- попытка изменить роль через профиль;
- попытка изменить статус аккаунта через профиль;
- невалидные символы и экстремально длинные строки в профильных полях.

## 3. Habits

### Назначение

Контур отвечает за список привычек, создание, просмотр детали, редактирование,
архивирование, возврат из архива и необратимое удаление привычки.

### Сценарии

- получить список своих привычек;
- создать привычку;
- открыть детали привычки;
- изменить сведения о привычке;
- архивировать привычку;
- вернуть привычку из архива;
- необратимо удалить привычку.

### Закрываемые требования

- FR-04;
- FR-05;
- FR-06;
- FR-07;
- FR-08;
- FR-09;
- FR-10;
- FR-16;
- FR-17;
- NFR-02;
- NFR-03;
- NFR-04;
- NFR-08.

### Обязательные проверки доступа

- пользователь видит только свои привычки;
- пользователь не может открыть, изменить, архивировать или удалить чужую
  привычку;
- неавторизованный пользователь не может работать с привычками;
- заблокированный пользователь не может работать с привычками;
- администратор не получает автоматическое право вмешиваться в личные привычки
  пользователя как часть MVP.

### Невалидные данные для будущей валидации и фаззинга

- пустое название привычки;
- слишком длинное название или описание;
- невалидный режим периодичности;
- пустой список дней недели при режиме выполнения по выбранным дням;
- недопустимые значения дней недели;
- повторяющиеся дни недели в периодичности;
- попытка передать выбранные дни недели для ежедневного режима;
- попытка архивировать уже архивную привычку;
- попытка вернуть из архива активную привычку;
- попытка удалить чужую привычку;
- некорректные идентификаторы привычек.

Соглашение API для `weekdays`: значения передаются числами `0..6`, где
`0 = Monday`, `1 = Tuesday`, `2 = Wednesday`, `3 = Thursday`, `4 = Friday`,
`5 = Saturday`, `6 = Sunday`. Это совпадает с Python `date.weekday()`.

## 4. Habit completions

### Назначение

Контур отвечает за отметку выполнения привычки за дату, изменение или снятие
ошибочной отметки и получение истории выполнения.

### Сценарии

- отметить выполнение привычки за конкретную дату;
- снять ошибочную отметку;
- получить историю выполнения привычки.

### Закрываемые требования

- FR-11;
- FR-12;
- FR-13;
- FR-14;
- FR-17;
- NFR-02;
- NFR-03;
- NFR-08.

### Обязательные проверки доступа

- пользователь может отмечать выполнение только своих привычек;
- пользователь не может изменять отметки чужой привычки;
- неавторизованный пользователь не может работать с отметками;
- заблокированный пользователь не может работать с отметками;
- система не должна создавать дублирующиеся отметки для одной привычки и одной
  даты;
- система должна запрещать отметку выполнения в незапланированный день.

### Невалидные данные для будущей валидации и фаззинга

- невалидная дата;
- дата в некорректном формате;
- дата за пределами допустимого диапазона;
- отметка для несуществующей привычки;
- отметка для чужой привычки;
- повторная отметка одной привычки на одну дату;
- попытка изменить несуществующую отметку;
- попытка отметить выполнение в незапланированный день;
- попытка снять отметку, которой не существует.

## 5. Statistics / dashboard

### Назначение

Контур отвечает за получение статистики по одной привычке и общего дашборда
пользователя.

### Сценарии

- получить статистику по одной привычке;
- получить общий дашборд пользователя по привычкам.

Фактические endpoint текущего MVP:

- `GET /api/habits/{habit_id}/statistics/` — статистика по одной привычке
  текущего пользователя;
- `GET /api/dashboard/` — компактный дашборд по активным привычкам текущего
  пользователя.

Dashboard возвращает только active habits. Архивные привычки доступны для
чтения статистики по конкретной привычке, но не входят в общий dashboard.
Если в расчетном периоде нет ни одной запланированной даты,
`compliance_percent` возвращается как `null`.

`completion_count` отражает общее количество completion-записей в расчетном
периоде. `completed_scheduled_dates_count` отражает количество запланированных
дат периода, для которых есть completion. При корректных API-данных MVP эти
значения обычно совпадают, но второе поле явно связывает отметки с плановыми
датами и используется для расчета `compliance_percent`.

### Закрываемые требования

- FR-13;
- FR-14;
- FR-15;
- FR-17;
- NFR-03;
- NFR-04;
- NFR-08.

### Обязательные проверки доступа

- пользователь получает статистику только по своим привычкам;
- неавторизованный пользователь не получает статистику;
- заблокированный пользователь не получает статистику;
- расчет серии и процента соблюдения должен учитывать периодичность привычки;
- процент соблюдения в MVP считается за весь период отслеживания привычки:
  для активной привычки от даты создания до текущей даты, для архивной — от
  даты создания до даты архивирования.

### Невалидные данные для будущей валидации и фаззинга

- статистика по несуществующей привычке;
- статистика по чужой привычке;
- попытка передать пользовательский период расчета, если API MVP не
  поддерживает выбор периода;
- невалидные параметры фильтрации.

## 6. Admin

### Назначение

Контур отвечает за административные сценарии: вход через общий механизм
аутентификации, просмотр пользователей, просмотр статуса, блокировка и
разблокировка учетной записи, отказ обычному пользователю при попытке вызова
admin-функции.

### Сценарии

- вход администратора через общий механизм аутентификации с проверкой роли;
- получить список пользователей;
- получить сведения о статусе пользователя;
- заблокировать пользователя;
- разблокировать пользователя;
- отказать обычному пользователю при попытке вызова административной функции.

Фактические endpoint текущего MVP:

- `GET /api/admin/users/` — список пользователей без пагинации;
- `GET /api/admin/users/{user_id}/` — данные пользователя;
- `POST /api/admin/users/{user_id}/block/` — блокировка пользователя;
- `POST /api/admin/users/{user_id}/unblock/` — разблокировка пользователя.

Доступ к admin endpoint имеет только active admin. Обычный пользователь,
анонимный пользователь и заблокированный admin не получают доступ. `block` и
`unblock` идемпотентны: повторный вызов возвращает актуальное состояние без
лишнего изменения данных. Self-block запрещен. После блокировки пользователя
новый login и refresh token не выдаются; уже выданный access token
ограничивается проверкой актуального `status` на защищенных endpoint.

### Закрываемые требования

- FR-18;
- FR-19;
- FR-20;
- FR-21;
- FR-22;
- NFR-01;
- NFR-02;
- NFR-08.

### Обязательные проверки доступа

- административные операции доступны только пользователю с ролью
  администратора;
- неавторизованный пользователь не может вызывать административные операции;
- обычный пользователь не может вызывать административные операции;
- пользователь не может получить административную роль через пользовательский
  ввод;
- невалидные значения роли должны отклоняться;
- невалидные значения статуса учетной записи должны отклоняться;
- блокировка пользователя должна лишать его доступа к пользовательским
  функциям.

### Невалидные данные для будущей валидации и фаззинга

- невалидное значение роли;
- попытка передать роль администратора при регистрации;
- попытка изменить роль через профиль;
- попытка обычного пользователя вызвать admin-сценарий;
- попытка неавторизованного пользователя вызвать admin-сценарий;
- некорректный идентификатор пользователя;
- попытка заблокировать несуществующего пользователя;
- попытка разблокировать несуществующего пользователя;
- невалидное значение статуса учетной записи;
- попытка изменить статус учетной записи вне административного контура;
- попытка обновить refresh token после блокировки учетной записи.

## 7. Что пока не фиксируется

На текущем этапе не фиксируются:

- точные URL;
- HTTP-коды;
- имена маршрутов;
- сериализаторы;
- поля request/response;
- конкретные библиотеки JWT;
- OpenAPI-схема;
- структура frontend-запросов;
- структура backend-приложений.

Эти решения принимаются после утверждения модели данных и перед реализацией.
