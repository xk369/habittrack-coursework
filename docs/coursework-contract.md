# Контракт курсовой работы

## Назначение документа

Документ фиксирует обязательные требования к курсовой работе по дисциплине
«Разработка клиент-серверных приложений» на тему «Трекер формирования
привычек». Контракт используется как единый источник контроля при анализе,
проектировании, реализации, тестировании, подготовке отчета и презентации.

## Приоритет источников

1. Утвержденный лист задания на курсовую работу.
2. Прямые требования и пояснения преподавателя.
3. Методические указания по курсовой работе.
4. Готовый отчет по прошлой курсовой: только как эталон оформления, структуры,
   логики изложения, качества формулировок, работы с рисунками, таблицами,
   ссылками и содержанием; не как источник предметного содержания.

## Утвержденная тема

«Трекер формирования привычек».

## Исходные данные

- Методология двенадцати факторов.
- Git.

Методология двенадцати факторов применяется на этапах архитектуры,
реализации, конфигурации, Docker/deploy и описания инженерных решений. Она не
используется вместо анализа предметной области.

## Границы продукта

Разрабатывается персональный веб-трекер формирования привычек для
индивидуальных пользователей.

Основная роль: пользователь.

Пользователь должен иметь возможность:

- регистрироваться и входить в систему;
- создавать, просматривать, редактировать и удалять привычки;
- отмечать выполнение привычек по дням;
- просматривать прогресс и статистику;
- работать с личным профилем.

Административная роль: администратор.

Администратор должен иметь возможность:

- просматривать пользователей;
- управлять состоянием учетных записей;
- контролировать доступ к административным функциям.

Административная роль нужна не номинально: ролевая модель должна быть
спроектирована, реализована и проверена так, чтобы выполнить требование задания
о валидации ролевой модели на некорректные данные.

## Обязательные результаты по листу задания

1. Провести анализ предметной области для выбранной темы.
2. Выбрать клиент-серверную архитектуру для приложения и детально описать ее с
   помощью UML.
3. Выбрать программный стек для реализации full-stack CRUD-приложения.
4. Разработать клиентскую и серверную части приложения.
5. Реализовать авторизацию и аутентификацию пользователя.
6. Обеспечить работу с базой данных.
7. Заполнить систему тестовыми данными.
8. Валидировать ролевую модель на некорректные данные.
9. Провести фаззинг-тестирование.
10. Разместить исходный код в системе контроля версий.
11. Добавить Dockerfile.
12. Описать структуру проекта в README-файле.
13. Развернуть клиент-серверное приложение в облаке.
14. Разработать презентацию с графическими материалами.

## Требования к анализу предметной области

Глава «Анализ предметной области» должна отвечать на вопрос: почему система
«Трекер формирования привычек» вообще нужна?

В анализе должны быть отражены:

- описание предметной области;
- что автоматизируется или привносится нового;
- актуальность и новизна проекта;
- AS-IS: как процесс формирования и отслеживания привычек работает сейчас без
  разрабатываемой системы;
- участники процесса;
- используемые данные;
- реальные проблемы предметной области;
- анализ не менее 3 актуальных аналогов;
- отличия разрабатываемой системы от аналогов;
- роли пользователей;
- концептуальные сущности предметной области;
- функциональные требования;
- нефункциональные требования;
- вывод по главе.

Каждое ключевое требование должно вытекать из выявленной проблемы.

## Запреты для главы анализа

В главе анализа предметной области нельзя преждевременно описывать:

- React;
- Node.js;
- Django;
- Spring Boot;
- JWT;
- Docker;
- REST API;
- PostgreSQL;
- MongoDB;
- ER-диаграмму;
- конкретную архитектуру реализации;
- иные детали проектирования и реализации.

## Требования к проектированию

Проектирование выполняется только после утверждения анализа предметной области
и требований.

Необходимо подготовить:

- обоснование клиент-серверной архитектуры;
- описание архитектуры с помощью UML;
- IDEF0-диаграмму;
- необходимые UML-диаграммы;
- ER-диаграмму или схему базы данных;
- адаптированную архитектурную диаграмму, подходящую под продукт;
- план диаграмм до их финальной генерации.

Диаграммы должны планироваться и согласовываться, а не создаваться хаотично.

## Требования к реализации

Реализация выполняется после анализа, требований, проектирования и выбора
стека.

Система должна включать:

- frontend;
- backend;
- CRUD-сценарии для привычек;
- регистрацию и вход;
- хранение информации о пользователе;
- работу с базой данных;
- тестовые данные;
- проверяемую ролевую модель;
- Dockerfile;
- README с описанием, стеком, структурой проекта и инструкцией запуска.

Запрещено приписывать проекту функции, механизмы, тесты, диаграммы или
инженерные решения, которых фактически нет в коде или артефактах.

## Требования к ролевой модели

Должны быть предусмотрены и позже проверены следующие сценарии:

- обычный пользователь не может получить admin-доступ через API;
- попытка регистрации или обновления данных с невалидной ролью корректно
  отклоняется;
- невалидные значения роли валидируются;
- доступ к admin-функциям запрещен неавторизованным пользователям;
- доступ к admin-функциям запрещен обычным пользователям;
- проверки ролевой модели входят в тестирование и фаззинг.

## Требования к тестированию

Необходимо предусмотреть:

- проверку работоспособности MVP;
- тестирование основных пользовательских сценариев;
- тестирование авторизации и аутентификации;
- тестирование CRUD-сценариев;
- проверку некорректных данных ролевой модели;
- фаззинг-тестирование.

Фаззинг-тестирование является обязательной частью проекта и должно быть
заложено заранее.

## Требования к GitHub, Docker, README и deploy

Необходимо:

- вести Git-репозиторий в активном состоянии;
- разместить проект на GitHub;
- фиксировать значимые коммиты;
- добавить Dockerfile;
- подготовить README с описанием проекта, стеком, структурой и запуском;
- развернуть приложение в облаке;
- собрать доказательную базу: ссылки, скриншоты, результаты тестов, сведения о
  deploy.

## Требования к отчету

Отчет готовится по методическим указаниям и применимым требованиям ГОСТ.

Структура должна включать:

- задание на курсовую работу;
- титульный лист;
- аннотацию;
- содержание;
- перечень сокращений, условных обозначений, символов, единиц и терминов —
  при необходимости;
- введение;
- основную часть;
- заключение;
- список использованных источников;
- приложения — при необходимости.

Финальное решение о наличии раздела с перечнем сокращений, условных
обозначений, символов, единиц и терминов принимается ближе к сборке отчета.

Финальный отчет собирается только после стабилизации фактической реализации.

## Требования к презентации

Презентация должна включать:

- титульный слайд;
- цель и задачи курсовой работы;
- полный цикл создания продукта: целеполагание, анализ предметной области,
  проектирование, реализация, тестирование, документирование;
- графические материалы;
- результаты, выносимые на защиту;
- выводы;
- финальный слайд.

Финальная презентация собирается после согласования фактических результатов и
структуры защиты.

## Матрица трассировки

На протяжении всей работы ведется матрица:

Проблема -> Требование -> Проектное решение -> Реализация -> Проверка.

Матрица должна связывать анализ предметной области с требованиями,
архитектурой, кодом и тестами.

## Контрольные остановки

Перед переходом дальше требуется подтверждение пользователя после:

1. Фиксации требований и дорожной карты.
2. Product brief.
3. Анализа предметной области и требований.
4. Проектирования архитектуры и плана диаграмм.
5. Финальной сборки отчета.
6. Финальной сборки презентации.
