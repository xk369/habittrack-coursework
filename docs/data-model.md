# Концептуальная модель данных

## Статус

Документ фиксирует предметную модель HabitTrack на уровне будущих сущностей,
связей и правил хранения. Здесь не задаются SQL-типы, миграции, индексы,
ER-диаграмма и детали реализации.

## 1. Общая идея модели

Модель данных HabitTrack должна поддерживать персональное хранение привычек,
их периодичности, выбранных дней недели, отметок выполнения, истории,
состояния привычки, роли пользователя и статуса учетной записи. Центральная
линия модели:

пользователь -> привычки -> расписание -> выбранные дни расписания -> отметки
выполнения -> история и расчет статистики.

Роли и статусы остаются важными предметными понятиями, но в MVP не
проектируются как отдельные справочные таблицы. На уровне будущей реализации
они задаются как строго ограниченные значения атрибутов User:

- role: `user` / `admin`;
- status: `active` / `blocked`.

Невалидные значения роли и статуса должны отклоняться.

## 2. Сущности

### User

Назначение: представляет учетную запись человека, который работает с системой
как обычный пользователь или администратор.

Ключевые смысловые поля:

- идентификатор пользователя;
- email как поле входа;
- базовые сведения профиля;
- роль: `user` или `admin`;
- статус учетной записи: `active` или `blocked`;
- дата создания учетной записи;
- дата последнего изменения учетной записи.

Связи:

- один User может иметь много Habit;
- администратор как User может выполнять служебные действия над статусом
  других учетных записей.

Закрываемые требования:

- FR-01, FR-02, FR-03;
- FR-17-FR-22;
- NFR-01, NFR-02.

Правила:

- роль нельзя подменять пользовательским вводом;
- статус нельзя подменять пользовательским вводом;
- заблокированный User не получает доступ к пользовательским функциям.

### Role

Назначение: предметное понятие, определяющее уровень доступа пользователя.

В MVP Role не является отдельной сущностью ER-модели и не проектируется как
отдельная таблица-справочник. Роль хранится как строго ограниченное значение
атрибута User.

Допустимые значения:

- `user`;
- `admin`.

Закрываемые требования:

- FR-17, FR-18, FR-21, FR-22;
- NFR-01, NFR-02, NFR-08.

### AccountStatus

Назначение: предметное понятие, определяющее состояние учетной записи и
возможность пользователя работать с системой.

В MVP AccountStatus не является отдельной сущностью ER-модели и не
проектируется как отдельная таблица-справочник. Статус хранится как строго
ограниченное значение атрибута User.

Допустимые значения:

- `active`;
- `blocked`.

Закрываемые требования:

- FR-19, FR-20, FR-21;
- NFR-01.

### Habit

Назначение: представляет привычку пользователя как повторяющееся действие с
целью, состоянием и правилами выполнения.

Ключевые смысловые поля:

- идентификатор привычки;
- владелец привычки;
- название привычки;
- краткая цель привычки (purpose);
- состояние привычки: активная или архивная;
- дата создания;
- дата изменения;
- дата архивирования, если привычка архивирована.

Связи:

- Habit принадлежит одному User;
- Habit имеет одно HabitSchedule;
- Habit имеет много HabitCompletion;
- Habit используется как источник данных для истории и статистики.

Закрываемые требования:

- FR-04-FR-09;
- FR-16, FR-17;
- NFR-03, NFR-04.

### HabitSchedule

Назначение: описывает режим периодичности выполнения привычки.

Ключевые смысловые поля:

- идентификатор расписания;
- связанная привычка;
- режим периодичности: ежедневно или по выбранным дням недели.

Минимальные режимы MVP:

- ежедневно;
- по выбранным дням недели.

Связи:

- HabitSchedule относится к одной Habit;
- HabitSchedule имеет много HabitScheduleDay, если выбран режим выполнения по
  дням недели;
- HabitSchedule используется при проверке допустимости отметки выполнения и
  при расчете серии и процента соблюдения.

Закрываемые требования:

- FR-10, FR-11, FR-13, FR-14;
- NFR-02.

### HabitScheduleDay

Назначение: фиксирует один выбранный день недели для расписания привычки.

Ключевые смысловые поля:

- идентификатор записи выбранного дня;
- связанное расписание;
- день недели.

Соглашение по значениям `weekday`:

- `0` — Monday;
- `1` — Tuesday;
- `2` — Wednesday;
- `3` — Thursday;
- `4` — Friday;
- `5` — Saturday;
- `6` — Sunday.

Это соглашение соответствует Python `date.weekday()` и используется при
проверке допустимости даты выполнения привычки.

Связи:

- HabitScheduleDay относится к одному HabitSchedule;
- один HabitSchedule может иметь несколько HabitScheduleDay;
- для одного HabitSchedule один и тот же день недели не должен повторяться.

Закрываемые требования:

- FR-10, FR-11, FR-13, FR-14;
- NFR-02.

### HabitCompletion

Назначение: фиксирует факт выполнения привычки за конкретную дату.

Ключевые смысловые поля:

- идентификатор отметки;
- связанная привычка;
- дата выполнения;
- дата создания отметки;
- дата изменения отметки.

Связи:

- HabitCompletion относится к одной Habit;
- набор HabitCompletion образует историю выполнения Habit;
- HabitCompletion используется для расчета серии, процента соблюдения и
  дашборда.

Закрываемые требования:

- FR-11, FR-12, FR-13, FR-14, FR-15;
- NFR-02, NFR-03, NFR-08.

Правила:

- запись HabitCompletion существует, если привычка выполнена за дату;
- отсутствие записи HabitCompletion на запланированную дату трактуется как
  отсутствие выполнения;
- снятие ошибочной отметки выполняется удалением соответствующей записи
  HabitCompletion;
- отдельное поле состояния отметки в MVP не требуется;
- для одной Habit и одной даты не должно быть дублирующихся completion-записей;
- выполнение можно отмечать только за дату, соответствующую расписанию
  привычки.

### Агрегированная статистика

В MVP не вводится отдельная сущность для хранения агрегированной статистики.
Базовая статистика вычисляется из HabitSchedule, HabitScheduleDay и
HabitCompletion при запросе или в прикладной логике.

Аргументы:

- источником правды остается история отметок выполнения;
- статистика в MVP ограничена текущей серией, количеством выполнений и
  процентом соблюдения;
- отдельное хранение агрегатов создало бы риск рассинхронизации с отметками;
- вычисление из отметок проще проверять тестами и фаззингом;
- для учебного MVP объем данных ожидается умеренным.

Закрываемые требования:

- FR-13, FR-14, FR-15;
- NFR-03, NFR-08.

## 3. Бизнес-правила хранения и обработки данных

1. У пользователя может быть много привычек.
2. Обычный пользователь работает только со своими привычками.
3. Привычка имеет состояние: активная или архивная.
4. Архивирование не удаляет отметки выполнения.
5. Удаление привычки является необратимым действием и удаляет связанные
   отметки выполнения.
6. Для необратимого удаления привычки требуется подтверждение на уровне UI.
7. Backend рассматривает удаление как отдельную необратимую операцию с
   удалением связанных данных.
8. Периодичность MVP поддерживает два варианта: ежедневно и по выбранным дням
   недели.
9. HabitSchedule задает режим периодичности.
10. HabitScheduleDay фиксирует один выбранный день недели.
11. Для одного HabitSchedule один и тот же день недели не должен
    дублироваться.
12. Отметка выполнения должна быть привязана к привычке и конкретной дате.
13. Отметку выполнения можно создать только за дату, которая соответствует
    расписанию привычки.
14. Для одной привычки и одной даты не должно возникать дублирующихся отметок
    выполнения.
15. В MVP даты выполнения, дата создания привычки при сравнении и расчет
    текущей даты интерпретируются в `TIME_ZONE` проекта; пользовательские
    таймзоны отдельно не поддерживаются.
16. Текущая серия должна рассчитываться с учетом запланированных дат, а не
    любых календарных дней подряд.
17. Процент соблюдения в MVP считается за весь период отслеживания привычки.
18. Для активной привычки период расчета процента соблюдения идет от даты
    создания до текущей даты.
19. Для архивной привычки период расчета процента соблюдения идет от даты
    создания до даты архивирования.
20. Процент соблюдения рассчитывается как отношение выполненных запланированных
    дат к общему числу запланированных дат за выбранный период.
21. Блокировка аккаунта запрещает доступ к пользовательским функциям.
22. Роль и статус аккаунта нельзя подменять пользовательским вводом.
23. Невалидные значения роли и статуса должны отклоняться.
24. Административные действия не должны давать администратору роль участника
    личного процесса формирования привычек пользователя.

## 4. Детали, которые могут быть уточнены при реализации

Перед ER-диаграммой ключевые спорные решения закрыты. До реализации могут быть
уточнены только детали, не меняющие предметную модель:

- точный способ подтверждения необратимого удаления в UI;
- точные названия ограниченных значений для режимов расписания и состояния
  привычки;
- способ организации сервисного слоя для расчета статистики внутри backend.
