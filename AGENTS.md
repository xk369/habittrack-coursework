# AGENTS.md

## Проект

Курсовая работа по дисциплине «Разработка клиент-серверных приложений».

Тема: «Трекер формирования привычек».

Перед созданием или изменением пользовательского интерфейса необходимо читать
`DESIGN.md` в корне репозитория и сохранять описанный там визуальный контракт:
рабочий dashboard-first интерфейс, компактные метрики, единый primary accent,
табличную читаемость чисел и аккуратные responsive-состояния.

Проект выполняется как цельный инженерный цикл:

1. Анализ предметной области.
2. Требования.
3. Проектирование.
4. Реализация.
5. Тестирование.
6. Документация.
7. Отчет по методическим указаниям и ГОСТ.
8. Презентация.

Нельзя вести работу как набор разрозненных задач. Каждый этап должен
поддерживать последующие этапы и быть связан с матрицей трассировки.

## Приоритет источников

При конфликте требований использовать следующий порядок приоритета:

1. Утвержденный лист задания на курсовую работу.
2. Прямые требования и пояснения преподавателя.
3. Методические указания по курсовой работе.
4. Прошлый готовый отчет только как эталон оформления, структуры документа,
   логики изложения, качества формулировок, работы с рисунками, таблицами,
   ссылками и содержанием.

Прошлый отчет запрещено использовать как источник предметного содержания для
текущей темы.

## Утвержденные границы продукта

Разрабатывается персональный веб-трекер формирования привычек для
индивидуальных пользователей.

Основная роль: пользователь.

Пользователь:

- регистрируется и входит в систему;
- создает, просматривает, редактирует и удаляет привычки;
- отмечает выполнение привычек по дням;
- просматривает прогресс и статистику;
- работает с личным профилем.

Административная роль: администратор.

Администратор:

- просматривает пользователей;
- управляет состоянием учетных записей;
- контролирует доступ к административным функциям.

Административная роль должна быть реальной частью продукта, а не формальной
строкой в отчете. Ее необходимо спроектировать, реализовать и проверить.

## Главный запрет ранних этапов

До утверждения анализа предметной области и требований запрещено выбирать или
фиксировать финальные:

- программный стек;
- базу данных;
- API;
- UI;
- конкретную архитектуру реализации;
- ER-диаграмму или схему БД;
- детали Docker/deploy как готовое решение.

На ранних этапах можно фиксировать только ограничения задания и будущие
обязательные области работы.

## Анализ предметной области

Глава «Анализ предметной области» должна отвечать на вопрос:

Почему система «Трекер формирования привычек» вообще нужна?

В этой главе необходимо исследовать:

- что автоматизируется или привносится нового;
- актуальность и новизну проекта;
- как процесс формирования и отслеживания привычек работает сейчас без системы
  (AS-IS);
- участников процесса;
- используемые данные;
- реальные проблемы предметной области;
- не менее 3 актуальных аналогов;
- отличия разрабатываемой системы от аналогов;
- роли пользователей;
- концептуальные сущности предметной области;
- функциональные требования;
- нефункциональные требования;
- вывод по главе.

Требования должны вытекать из выявленных проблем, а не появляться без
обоснования.

## Запрет для главы анализа

Запрещено превращать анализ предметной области в описание технологий.

В первой главе нельзя преждевременно писать про:

- React;
- Node.js;
- Django;
- Spring Boot;
- JWT;
- Docker;
- REST API;
- PostgreSQL;
- MongoDB;
- ER-диаграмму;
- конкретную архитектуру реализации;
- любые другие детали реализации, если они подменяют анализ предметной области.

Технологии, архитектура, БД, API и интерфейсы появляются только после анализа
процессов, проблем и требований.

## Матрица трассировки

На протяжении всей работы обязательно вести матрицу:

Проблема -> Требование -> Проектное решение -> Реализация -> Проверка.

Матрица должна использоваться для контроля того, что:

- каждое важное требование имеет источник в проблеме предметной области;
- каждое проектное решение связано с требованием;
- реализация не расходится с проектированием;
- тесты и фаззинг проверяют заявленные требования;
- в отчет не попадает то, чего нет в реализации.

Основной файл матрицы: `docs/traceability-matrix.md`.

## Контрольные остановки

После следующих этапов необходимо остановиться и запросить подтверждение
пользователя перед продолжением:

1. Фиксация требований и дорожной карты.
2. Product brief.
3. Анализ предметной области и требования.
4. Проектирование архитектуры и план диаграмм.

6. Финальная сборка презентации.

Если пользователь явно не подтвердил переход, не перескакивать на следующий
этап.

## Проектирование и диаграммы

Диаграммы сначала планируются и согласовываются, затем создаются.

Нельзя генерировать диаграммы хаотично или задним числом под уже написанный
текст. Набор диаграмм должен быть связан с требованиями задания и логикой
проекта.

Обязательные области проектирования:

- обоснование клиент-серверной архитектуры;
- описание архитектуры с помощью UML;
- IDEF0;
- необходимые UML-диаграммы;
- ER-диаграмма или схема БД;
- адаптированная архитектурная диаграмма, по которой понятна архитектура
  продукта;
- описание применения методологии двенадцати факторов на инженерных этапах.

Методология двенадцати факторов применяется при архитектуре, реализации,
конфигурации, Docker/deploy и описании инженерных решений. Она не заменяет
анализ предметной области.

## Реализация

Реализация начинается только после утверждения анализа, требований,
архитектурного направления и плана диаграмм.

Обязательные области реализации:

- клиентская часть;
- серверная часть;
- CRUD для привычек;
- регистрация и вход;
- авторизация и аутентификация пользователя;
- работа с базой данных;
- заполнение тестовыми данными;
- ролевая модель;
- административные функции;
- Dockerfile;
- README с описанием, стеком, структурой проекта и инструкцией запуска;
- подготовка к облачному deploy.

Запрещено приписывать проекту функции, архитектурные свойства, тесты или
инфраструктурные возможности, которых реально нет в коде или артефактах.

## Ролевая модель и некорректные данные

Требование задания о валидации ролевой модели на некорректные данные является
обязательным.

Необходимо предусмотреть реализацию и проверку следующих случаев:

- обычный пользователь не может получить admin-доступ через API;
- попытка регистрации или обновления данных с невалидной ролью отклоняется;
- невалидные значения роли валидируются;
- admin-функции недоступны неавторизованным пользователям;
- admin-функции недоступны обычным пользователям;
- эти проверки включены в тестирование;
- эти проверки учитываются при фаззинг-тестировании.

Рабочий файл: `docs/role-model-validation.md`.

## Тестирование и фаззинг

Фаззинг-тестирование является обязательной частью проекта и должно быть
заложено заранее, а не добавлено в последний момент.

Необходимо планировать:

- проверку MVP;
- проверку основных пользовательских сценариев;
- проверку CRUD;
- проверку регистрации, входа, авторизации и аутентификации;
- проверку административных функций;
- проверку некорректных данных ролевой модели;
- фаззинг API и точек ввода;
- фиксацию результатов тестирования для отчета и презентации.

Рабочие файлы:

- `docs/test-plan.md`;
- `docs/fuzzing-plan.md`;
- `docs/role-model-validation.md`.

## Отчет

Отчет должен соответствовать методическим указаниям по курсовой работе и
применимым требованиям ГОСТ.

Структура отчета:

- задание на курсовую работу;
- титульный лист;
- аннотация;
- содержание;
- перечень сокращений, условных обозначений, символов, единиц и терминов —
  при необходимости;
- введение;
- основная часть;
- заключение;
- список использованных источников;
- приложения — при необходимости.

Финальное решение о наличии раздела с перечнем сокращений, условных
обозначений, символов, единиц и терминов принимается ближе к сборке отчета.

Финальный отчет собирается только после стабилизации фактической реализации.
Нельзя писать отчет так, будто функции уже существуют, если они еще не
реализованы и не проверены.

Рабочий файл: `docs/report-outline.md`.

Финальная сборка презентации выполняется только после согласования фактических

Рабочий файл: `docs/presentation-outline.md`.
