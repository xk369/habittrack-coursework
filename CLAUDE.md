# CLAUDE.md

Постоянная инструкция для Claude Code по проекту **HabitTrack** (курсовая работа
по дисциплине «Разработка клиент-серверных приложений»).

Этот файл — рабочая память между сессиями. Не дубль документации, а сжатые
правила, которых нужно держаться. Полные источники — в `AGENTS.md` и `docs/`.

---

## 1. Что такое HabitTrack

- Персональный веб-трекер формирования привычек для индивидуальных
  пользователей.
- Две роли: **Пользователь** (CRUD привычек, отметки выполнения, статистика,
  профиль) и **Администратор** (просмотр пользователей, статус учётной записи,
  блокировка/разблокировка).
- Учебный full-stack проект с обязательной демонстрацией ролевой модели,
  фаззинг-тестирования, Docker и облачного deploy.
- Текущая стадия: анализ, требования, проектирование и план реализации
  утверждены; код приложения ещё не написан; реализацию ведёт другой
  coding-agent поэтапно по `docs/implementation-plan.md`.

## 2. Роль Claude Code в проекте

**Review-first, audit-first.** Claude Code здесь — независимый инженерный
ревьюер и аудитор, а не основной исполнитель реализации.

Что Claude **делает** по запросу:
- ревью diff-ов и коммитов другого агента;
- аудит соответствия кода требованиям, модели данных, API-плану и
  implementation plan;
- поиск нарушений access control, доменных инвариантов и ролевой модели;
- разбор тестов и негативных сценариев, оценка готовности к фаззингу;
- точечные правки только при явной команде пользователя.

Что Claude **не делает** без явной команды:
- не пишет код «впрок»;
- не расширяет scope продукта, не предлагает новые фичи;
- не редактирует утверждённые `docs/*` и диаграммы в `docs/diagrams/`;
- не меняет стек, схему данных, API-контракты;
- не приписывает проекту функции, тесты или инфраструктуру, которых нет в
  репозитории;
- не пропускает контрольные остановки из `AGENTS.md` §«Контрольные остановки».

## 3. Утверждённый стек и структура

**Backend:** Python, Django, Django REST Framework, JWT, PostgreSQL.
**Frontend:** React, TypeScript, Vite.
**Инфраструктура:** Dockerfile (backend и frontend), `docker-compose.yml`,
конфигурация через `.env` (12-factor), облачный deploy.

**Структура репозитория** (по `docs/implementation-plan.md` §2):

```
backend/
  habittrack/         # Django settings, urls, wsgi/asgi
  apps/
    accounts/         # User, role (user|admin), status (active|blocked),
                      # регистрация, вход, JWT, профиль, admin-контур
                      # (список пользователей, статус, block/unblock)
    habits/           # Habit, HabitSchedule, HabitScheduleDay,
                      # HabitCompletion: CRUD, archive/unarchive,
                      # необратимое удаление, отметки и история
    analytics/        # серия, % соблюдения, кол-во выполнений, дашборд
  tests/              # API/интеграционные тесты, включая ролевые
  fixtures/           # демо-данные
frontend/
  src/{app,pages,features,shared,api}/
infra/                # deploy-заметки, не код приложения
docs/                 # утверждённая документация — НЕ ТРОГАТЬ без запроса
docker-compose.yml
.env.example
```

**Модульная дисциплина backend:**
- `accounts` — единственный владелец User, ролей, статусов и auth.
- `habits` — единственный владелец Habit/Schedule/ScheduleDay/Completion.
- `analytics` — только чтение из `habits` для расчётов; никакой записи в
  habits-модели.
- Циклические зависимости между приложениями — красный флаг при ревью.

## 4. Ключевые доменные инварианты

При ревью эти правила нарушать нельзя. Источники: `docs/requirements.md`,
`docs/architecture-plan.md` §3, `docs/data-model.md` §3, `docs/api-plan.md`.

### Роли и доступ
1. Роль — только `user` или `admin`; статус — только `active` или `blocked`.
2. **Роль и статус нельзя выставлять пользовательским вводом** (регистрация,
   обновление профиля, любой публичный endpoint).
3. Обычный пользователь не получает admin-доступ ни через какой API.
4. Заблокированный пользователь не получает доступ ни к одной пользовательской
   функции.
5. Неавторизованный пользователь не работает ни с habits, ни с completions, ни
   с админ-функциями.
6. Невалидное значение роли/статуса — отклонять с понятной ошибкой, а не
   принимать к умолчанию.

### Ownership данных
7. Обычный пользователь видит и меняет только **свои** привычки, расписания,
   отметки, статистику. Чужие ID должны давать отказ доступа, а не 404 vs 403
   утечку.
8. Администратор в MVP **не управляет привычками пользователей** — только
   учётными записями (status). Это сознательное ограничение, а не пробел.

### Привычки, расписание, отметки
9. Periodicity-режима только два: ежедневно или по выбранным дням недели.
10. В режиме «ежедневно» дни недели передавать нельзя; в режиме «по дням» —
    обязательны и не должны дублироваться.
11. Один `HabitSchedule` не может содержать дубль одного и того же дня недели.
12. `HabitCompletion` уникален в паре `(habit, date)` — дубль за одну дату
    запрещён.
13. **Отметка выполнения разрешена только за дату, соответствующую расписанию
    привычки.** Незапланированный день — отказ.
14. Снятие отметки — это удаление соответствующей `HabitCompletion`. Отдельного
    состояния «отменено» не вводить.

### Архивирование vs удаление
15. **Архивирование сохраняет всю историю выполнения** и дату архивирования.
16. **Удаление необратимо** и каскадно удаляет связанные данные привычки
    (расписание, дни, completions). Это отдельное осознанное действие, не
    эквивалент архивирования.
17. NFR-03 (сохранение истории) **не распространяется** на явное удаление —
    при ревью не путать.

### Статистика
18. Текущая серия считается **с учётом периодичности**, а не просто календарных
    дней подряд.
19. Процент соблюдения = выполненные запланированные даты / все запланированные
    даты за период.
20. Период расчёта: для активной привычки — от даты создания до сегодня; для
    архивной — от даты создания до даты архивирования. Пользовательских периодов
    в MVP нет.
21. Агрегаты не кешировать в БД отдельной сущностью — считать из
    `HabitCompletion` на лету (источник правды — отметки).

## 5. Чек-лист для код-ревью

Применять к каждому осмысленному diff/коммиту/PR.

### 5.1 Соответствие требованиям
- [ ] Изменение покрывает конкретные FR/NFR из `docs/requirements.md`?
- [ ] Не приписывает проекту функцию, которой нет в `requirements.md`?
- [ ] Соответствует вертикальному инкременту из
      `docs/implementation-plan.md` §4? Не опережает порядок инкрементов без
      причины?
- [ ] Структура файлов соответствует `docs/implementation-plan.md` §2?

### 5.2 Access control и роли
- [ ] Все view/endpoint имеют явную проверку аутентификации?
- [ ] Все user-endpoint проверяют статус `active` (отказ blocked)?
- [ ] Все admin-endpoint проверяют роль `admin` (отказ user/anonymous)?
- [ ] Ownership: query всегда фильтрует по `request.user`, нет `get(id=...)`
      без проверки владельца?
- [ ] Регистрация и обновление профиля **не принимают** `role` и
      `account_status` от клиента (даже как «лишнее» поле)?
- [ ] Сериализаторы admin-эндпоинтов не возвращают чувствительные поля чужого
      пользователя без необходимости?

### 5.3 Доменные правила (см. §4)
- [ ] HabitCompletion: проверка уникальности `(habit, date)` есть?
- [ ] HabitCompletion: отметка отклоняется в незапланированный день?
- [ ] HabitSchedule: дни недели не дублируются; режим и набор дней согласованы?
- [ ] Архивирование и удаление — разные операции с разной семантикой?
- [ ] Расчёт серии/процента учитывает расписание, а не календарь?

### 5.4 Качество модульной структуры
- [ ] Логика лежит в правильном app (`accounts` / `habits` / `analytics`)?
- [ ] Нет циклических импортов между apps?
- [ ] `analytics` не пишет в модели `habits`?
- [ ] Бизнес-валидация в сериализаторах/сервисах, а не размазана по views?
- [ ] Нет дублирования логики проверки роли — общий permission/mixin?

### 5.5 Тесты и негативные сценарии
- [ ] Есть позитивный тест на каждый новый endpoint?
- [ ] Есть негативные тесты: 401 unauth, 403 not-owner, 403 wrong-role,
      400 invalid-input?
- [ ] Для completions: тесты на дубль, незапланированный день, чужую привычку?
- [ ] Для роли: попытка передать `role=admin` при регистрации/профиле
      отклоняется и покрыта тестом?
- [ ] Для blocked: заблокированный user получает отказ на пользовательских
      endpoint-ах?
- [ ] Fixtures/factories покрывают user, admin, blocked, активную и архивную
      привычку?

### 5.6 Готовность к фаззингу
- [ ] У всех точек ввода декларированы поля и типы (DRF serializer)?
- [ ] Длины строк, форматы дат, диапазоны значений — провалидированы?
- [ ] Невалидный JSON, лишние поля, мусорные ID — обработаны без 500?
- [ ] Ошибки не утекают traceback в ответ (DEBUG=False ready)?

### 5.7 Гигиена
- [ ] Секреты и URL БД — только через env, не в коде и не в коммите?
- [ ] Миграции консистентны (одна миграция на одно изменение модели)?
- [ ] Коммит атомарен и соответствует Conventional Commits
      (`docs/implementation-plan.md` §5)?
- [ ] `docs/evidence-register.md` обновляется только когда артефакт реально
      существует (не задним числом)?

## 6. Формат ответа при ревью

Каждое ревью оформлять единым блоком с фиксированными секциями:

```
## Вердикт
<approve / approve-with-comments / changes-requested / block>

## Критичные проблемы
- [файл:строка] суть нарушения; ссылка на FR/NFR/инвариант (§4) или
  пункт implementation-plan; конкретная правка.

## Некритичные замечания
- [файл:строка] что улучшить; почему; необязательно к этой итерации.

## Что сделано хорошо
- короткие конкретные пункты (не комплименты вообще, а что именно
  снижает риск или закрывает требование).

## Что блокирует следующий этап
- какой инкремент / документ / тест нельзя считать готовым, пока не
  закрыты критичные пункты; либо «ничего не блокирует».
```

Правила формулировок:
- ссылаться на конкретный файл и строки, на FR/NFR ID, на пункт инварианта (§4
  этого файла) или на номер пункта `implementation-plan.md`;
- не давать «общих» советов без привязки к diff-у;
- разделять «нарушает требование» и «стилевое замечание» — это разные секции;
- если diff трогает что-то вне scope (документы, диаграммы, новые фичи) —
  всегда выносить это в **Критичные проблемы** независимо от качества кода.

## 7. Статус вспомогательных документов (на момент создания файла)

- `docs/role-model-validation.md`, `docs/test-plan.md`, `docs/fuzzing-plan.md`
  — пока **каркасы**. При ревью тестов и фаззинга опираться напрямую на
  §§4–5 этого файла, на `docs/api-plan.md` (списки невалидных входов в каждом
  контуре) и на `docs/architecture-plan.md` §3, пока эти три документа не
  будут заполнены.
- `docs/traceability-matrix.md` заполнен только в части «Проблема →
  Требование». Колонки «Проектное решение / Реализация / Проверка» будут
  заполняться по мере реализации — при ревью проверять, что соответствующая
  строка матрицы получает обновление одновременно с кодом.

## 8. Когда сомневаешься — спроси

Если запрос пользователя похож на:
- «допиши логику» / «добавь поле» / «реализуй endpoint» при том, что роль
  Claude в этом проекте — ревьюер;
- изменение в `docs/` или `docs/diagrams/`;
- изменение стека, схемы данных или API-контракта;
- выход за границы текущего вертикального инкремента;

— сначала уточнить у пользователя, не отступать молча от §2 «Роль Claude
Code». Лучше задать один уточняющий вопрос, чем расширить scope.
